Производство музейной страницы

Работать как оркестратор. Не копировать сюда нормы museum-core, тематического навыка или канонических стандартов и не заменять ими предметное решение.

1. Определить режим

Выбрать один режим до чтения страницы:

  • новая страница нового типа;
  • следующая страница принятой серии;
  • изменение существующей страницы;
  • добавление экспоната в существующую серию;
  • только медиапакет;
  • аудит без изменений;
  • изменение общего компонента, профиля или сборщика.

series-page означает новую самостоятельную страницу как следующую единицу принятой серии. add-exhibit означает новый предмет внутри уже существующей коллекционной страницы. Если предмет получает собственную страницу, выбрать series-page, а не add-exhibit.

Зафиксировать один музей, один выпуск, ожидаемую поставку и границу файлов. Для изменения существующего HTML соблюдать требование предварительного согласования из museum-core; аудит без изменений согласования не требует. Явная команда изменить страницу уже является разрешением в указанном объёме; не запрашивать её повторно для исправлений и проверок этого же пакета.

Для rewrite до кода зафиксировать принятую основу: каждое явное решение владельца, обязательный слот канона и функцию эталона. Разделить их на неизменяемо, можно переоформить, можно удалить только по отдельному решению. Запрос на упрощение, сокращение текста или новый визуальный язык сам по себе не разрешает удаление функции. Каждой неизменяемой строке заранее назначить данные/селектор и машинную либо браузерную проверку.

2. Загрузить только обязательный контекст

При первом применении полностью прочитать канонический museum-core, тематический навык выбранного музея и docs/standards/page-production-standard.md. Затем подключить обязательные редакторские и дизайнерские навыки по references/dependency-routing.md references/dependency-routing.md. Не заменять их мысленной проверкой и не читать соседние музеи. Уже прочитанные документы той же версии не загружать повторно без потери контекста или конкретного сомнения. Для продолжения локальной правки открыть затронутые разделы; обязательный состав и требования канона сохраняются.

Запустить перед работой из установленного skill:

GATE="$HOME/projects/russian-civilization/docs/skills/museum-page-production/scripts/page_gate.py"
/usr/bin/python3 "$GATE" preflight --project <корень-проекта> \
  --museum <slug> --mode <режим> [--page <путь-к-существующему-html>] \
  [--issue <паспорт-выпуска.json>]

Для new-museum, new-type, series-page, rewrite параметр --issue обязателен. При передаче другим агентам дополнительно запустить scripts/transfer-preflight.py по инструкции START-HERE.md переносимого пакета: обычный preflight не проверяет весь финальный delivery runtime.

Если канон, профиль, эталон, интерпретатор или инструмент не разрешаются однозначно, остановить сборку и назвать конфликт. Не выбирать копию по времени изменения.

3. Пройти G0–G7

Для новой страницы, существенной доводки и полного аудита применять references/editorial-panel.md references/editorial-panel.md и прочитать полный реестр ролей references/editorial-roles.json: D01–D15 — редакционная работа, R01–R15 — музейная панель, K01 — калибровка. Зафиксировать исполнителей и выходы до работы, замыкать замечания повторной проверкой. Для локальной правки повторять затронутые проходы с действительными доказательствами остальных.

До нового дизайна, типа страницы или интерактива прочитать канон /home/agent/projects/russian-civilization/rc-museum-production/standards/museum-competitor-research.md. Он задаёт сравнение России, зарубежья и цифровых музеев, карточки и передачу находок в реестр. Для следующей страницы серии выбрать применимые карточки в delta-брифе без полного нового обзора; после пилота вернуть результаты проверки в эти карточки.

Если новый канон ещё не интегрирован, прочитать зафиксированную версию: git -C /home/agent/projects/russian-civilization/rc-museum-production show a06ef2c:standards/museum-competitor-research.md; форму — a06ef2c:standards/templates/museum-competitor-study.md.

Во всех музеях применять museum-core, §5-бис (решение Сергея 14.09.2026): подбор нескольких самостоятельных цепляющих моментов и краткое основное чтение с раскрываемыми подробностями у каждого момента. До кода — карта моментов и источников в брифе; до сдачи — редакторская и браузерная проверка по канону. Это относится также к главной, залу и коллекции, а не только к странице дня.

Использовать краткую карту в references/gates.md references/gates.md. До кода заполнить assets/delta-brief.md assets/delta-brief.md, кроме режима чистого аудита. Для нового типа страницы требуется полный ШАГ 0 и принятый эталон; для принятой серии — delta-бриф и точный commit/SHA эталона.

Перед первым выпуском нового музея пройти references/museum-onboarding.md references/museum-onboarding.md. Общий skill при этом не переписывать: новый музей добавляет тематический навык и профиль своего типа страницы.

Не начинать сборку при незакрытых критических источниках, правах, календарном составе, главном предметном действии или обязательных материалах.

4. Строить из данных и профиля

Не считать HTML скрытым носителем стандарта. Зафиксировать:

  • общий профиль страницы и его версию;
  • тематический профиль музея;
  • тип страницы и обязательные/вариативные/неприменимые слоты;
  • структурированные данные выпуска;
  • доказательство функции каждого обязательного блока;
  • матрицу соответствия принятой концепции с источником каждого требования;
  • реестр начислений, если на странице есть баллы;
  • реестр экспонатов и прав, если страница показывает серию предметов.

Машинный контракт описан в references/profile-contract.md references/profile-contract.md. Производные значения — число экспонатов, длительность, вес, максимум баллов — получать из одного источника, а не поддерживать копиями в тексте.

Профиль не ослаблять под уже собранный HTML: запрещено выключать обязательный календарь, счёт, маршрут или удалять обязательный селектор ради зелёного аудита. Сначала профиль фиксирует принятую поставку, затем HTML проходит его.

Повторяемую разметку реализовывать общим компонентом или сборщиком. Сборщик обязан падать на отсутствующих данных и не создавать заглушки или выдуманное содержание.

5. Проверить до показа

При доводке, аудите и сдаче прочитать references/completion-loop.md references/completion-loop.md: сохранение принятой основы, закрытие замечаний повторной проверкой, честный учёт ролей и медиа, версия проверяющего инструмента и единый актуальный итог.

Запустить единый шлюз:

GATE="$HOME/projects/russian-civilization/docs/skills/museum-page-production/scripts/page_gate.py"
/usr/bin/python3 "$GATE" check --project <корень-проекта> \
  --museum <slug> --mode <режим> --issue <путь-к-issue.json> \
  --page <путь-к-html> --profile <путь-к-profile.json>

Для чистого аудита старой страницы --issue допустимо опустить. При допуске к публикации --issue обязателен в любом режиме и нужно добавить --publish; при доступном публичном адресе — --public-url <https-url>. Зелёный статический аудит не заменяет браузерную и предметную приёмку. Заполнить assets/acceptance-ledger.md assets/acceptance-ledger.md доказательствами, а не словами «выглядит нормально».

Для страницы-серии карикатур использовать профиль references/karikatura-collection.profile.json. Его машинные поля обязательны для новых страниц; на старой странице отсутствие полей фиксируется как долг, а не исправляется молча.

Для страницы произведения живописи использовать профиль references/art-work.profile.json. Он проверяет метаданные произведения, самостоятельность ролика и аудиогида, расшифровку, порядок смысловых слотов, честность глубины зума, вынесенные из полотна пояснения, точки деталей и бюджет первой загрузки. Для целого зала дополнительно запустить check-series по контракту references/series-contract.md references/series-contract.md:

/usr/bin/python3 "$GATE" check-series --project <корень-проекта> \
  --manifest <путь-к-series.json>

Не создавать сборщик нового типа страницы до принятия его профиля и одного эталона. После принятия сборщик рендерит страницу из структурированных данных, падает на пропусках и воспроизводит эталон в тестовой области до тиражирования.

Обязательная внутренняя петля:

машина → браузер → посетитель → предметный эксперт → текст → доступность и производительность → единый список замечаний → пакет исправлений → повтор.

Браузерную часть выполнять через принятый проектом инструмент реального браузера или навык Playwright. Единой команды для всех архетипов страницы нет: в реестре приёмки обязательно записать точную команду/сценарий, URL, ширины, успешный и ошибочный путь. Если в проекте нет воспроизводимого браузерного сценария, это незакрытое доказательство, а не основание объявить страницу готовой.

Для динамических обещаний вроде «сегодня» проверять источник даты и содержания, а не только текущий снимок экрана. Для крупной типографики отдельно проверять загруженный шрифт и визуальное пересечение строк: отсутствие overflow этого не доказывает. Интерактив с несколькими режимами проверять во всех режимах, включая согласованность подписей, чисел и суммарной длительности.

Если создаётся или меняется текст, применять rc-text к замыслу и готовому тексту. При чисто техническом исправлении не создавать новые варианты неизменяемого хука. Для первого экрана применять rc-hero; перед выдачей результата всегда применять rc-design-review. rc-artdirection нужен для новой визуальной системы или редизайна, но не для механического переноса принятого эталона.

После двух полных пакетных итераций проверить причину оставшихся ошибок. Продолжать адресные исправления в разрешённом объёме до результата или предела времени. К владельцу обращаться за действительно недостающим решением или доступом.

Проверить полноту ролевой петли

SKILL_ROOT="${CODEX_HOME:-$HOME/.codex}/skills/museum-page-production"
/usr/bin/python3 "$SKILL_ROOT/scripts/review_ledger.py" init \
  --page <html> --input <issue.json> --output <приёмка/review.json>
# Заполнить исполнителей, отчёты ролей и замечания по editorial-panel.md.
/usr/bin/python3 "$SKILL_ROOT/scripts/review_ledger.py" check <приёмка/review.json> --accept

init создаёт незаполненный реестр, а не успешную приёмку. Для аудита без правок вызвать check без --accept и сообщить открытые дефекты. До полной сдачи нужны и успешная проверка реестра, и существующие технические/предметные ворота.

6. Выдать точный статус

Для финальной технической сдачи применять rc-page.py deliver по действующему page-delivery-control.md. Не заменять его успехом отдельного чекера. Повторно использовать доказательства только при совпадении файлов, зависимостей и условий проверки; после правок повторить затронутые проверки и финальный шлюз.

Использовать один статус: черновик, предварительное превью, технически проверено, предметно принято, опубликовано, внешне проверено, принято владельцем. HTTP 200 доказывает только доступность адреса.

Перед словом «готово» указать: версию профиля, команды проверок, числа прошло/ошибка, браузерные ширины, проверенные медиа, публичный URL и оставшиеся долги.

7. Замкнуть повторяемую находку

До следующей страницы закрыть цепочку:

симптом → причина → каноническое правило → данные/профиль → общий компонент → регрессионная проверка → страницы-должники.

Не переносить случайное число или CSS одной страницы как общий стандарт. Не мигрировать принятые страницы задним числом без решения о версии и отдельной задачи.
